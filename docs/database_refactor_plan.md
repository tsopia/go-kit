# 数据库组件演进方案（草案）

围绕 `database` 包的体积与职责过于集中、错误模型不一致、可观测性扩展不足等问题，分阶段演进以降低风险。可按阶段交付，逐步落地。 

## 阶段 1：抽象与解耦
- 拆分核心职责为若干小组件并通过接口组合 `Database`：
  - `Connector`：负责配置验证、拨号、重试，返回 `*gorm.DB`。
  - `HealthChecker`：封装探针/查询测试，支持可取消 `context.Context`。 
  - `Executor`：承载 `Exec/Query/Tx` 等常规操作。
  - `Instrumentation`：统一日志/指标/Tracing Hook 注入，避免散落调用。
- 扩展对外接口：将健康检查、事务管理、底层访问（`Raw/SQLDB`）等能力纳入多个小接口，业务可按需依赖。 
- 统一错误包装：连接、事务、查询路径返回 `DatabaseError`，并按 `ErrorType` 分类，暴露辅助函数 `IsConnectionError` 等，便于调用方判定。

## 阶段 2：上下文与可靠性
- 让连接重试、健康检查、关闭钩子等流程接受外部 `context.Context`，支持可取消/超时控制。
- 在配置中新增启动超时、探针超时，并在重试时尊重上下文取消（避免阻塞启动）。
- 为连接池配置与重试策略增加单元测试覆盖，确保超时/重试行为符合预期。

## 阶段 3：可观测性与扩展
- 引入统一的 `Instrumentation`：
  - 日志：可插拔 logger 适配，统一结构化字段。
  - Metrics：接口预留（如 `Observer`）并在 Exec/Tx/HealthCheck 等关键路径打点。
  - Tracing：通过钩子在执行前后注入 span。
- 设计多数据源/读写分离契约：
  - 定义 `Connector` 返回 `Primary/Replica`，`Executor` 提供只读入口。
  - 通过策略接口控制路由（读/写选择、故障转移），便于未来扩展。

## 阶段 4：迁移与文档
- 以内部模块为粒度逐步迁移，保持 `DB` 接口向后兼容；必要时提供适配层。
- 补充 README/示例：包括新的接口分层、错误处理示例、可观测性接入方式。
- 针对新接口新增端到端测试（事务+健康检查+Instrumentation）。

> 以上为初步草案，可结合迭代优先级按阶段拆分需求单推进。
